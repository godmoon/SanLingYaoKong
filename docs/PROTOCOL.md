# 三菱电机 BLE 遥控协议（SanLingYaoKong 实现说明）

本文记录 SanLingYaoKong 实际使用的协议细节，来源为对原 App（`melremo.apk`）反编译代码的分析。
不同机型/固件可能存在差异，真机联调时请以日志页的原始帧为准。

## 1. GATT

服务：

```
0277df18-e796-11e6-bf01-fe55135034f3
```

特征：

| 用途 | UUID | 属性 |
| --- | --- | --- |
| 版本 | `799e3b22-e797-11e6-bf01-fe55135034f3` | read |
| 产品版本 | `def9382a-e795-11e6-bf01-fe55135034f3` | read |
| 写 | `e48c1528-e795-11e6-bf01-fe55135034f3` | write |
| 通知 | `ea1ea690-e795-11e6-bf01-fe55135034f3` | notify |

连接后先 `setCharacteristicNotification`，再写 CCCD `00002902-...` 开启通知，收到 `onDescriptorWrite` 后才算链路就绪。

### 写入方式

每片固定 20 字节，用 **无响应写入**（`WRITE_TYPE_NO_RESPONSE`），与原 App 的 `writeCharacteristic(characteristic, data, 1)` 一致。

关键点是**节流**：片与片之间至少 20 ms，帧与帧之间至少 30 ms（原 App 是 30 ms 定时器里最多发 3 片）。
这套固件如果被连续猛写，ATT 层会卡死：第一帧还能收到写回调，第二帧起 `onCharacteristicWrite` 永远不来，
2 秒后超时，之后所有 `writeCharacteristic` 都返回 false，最终 `status=133` 断链。
改用节流后连续收发几十帧都稳定。

`writeCharacteristic` 返回 false 说明协议栈还在忙上一笔，等 25 ms 重试，连续 8 次失败就判定协议栈卡死，主动断开重连。
写回调超时（300 ms）不当作失败——无响应写入本来就不依赖 ATT 应答，回调偶尔会迟到或丢失。

扫描过滤：设备名以 `M/R_`、`G/R_`、`M/R2` 开头，或广播里有 company ID `0x0014` 的厂商数据。

## 2. L1 帧

```
LE16 length | L1 header(1) | L2 PDU... | LE16 checksum
```

- `length` = L2 PDU 长度 + 1（L1 头）+ 2（校验和）
- `checksum` = length 低字节 + length 高字节 + L1 头及之后所有负载字节之和（按字节累加，取低 16 位）
- L1 头位域：

| 位 | 含义 |
| --- | --- |
| 0-2 | 序列号 `seq`（0~7 循环） |
| 3 | 方向：0=请求，1=响应 |
| 4-7 | 保留 |

请求的 `seq` 从 0 开始，每成功收到一帧响应后 +1（模 8）。设备会回显请求的 `seq`，因此可以用 `seq` 匹配响应。

## 3. L2 会话

L2 头：

| 位 | 含义 |
| --- | --- |
| 0 | first_snd_flg，请求固定为 1 |
| 1-2 | phase：0=开始会话，1=结束会话，2=数据 |
| 3-7 | 保留 |

开始/结束会话的 L2 负载：

```
[L2 头][登录块 7 字节]
```

数据帧的 L2 负载：

```
[L2 头][L3 请求]
```

L2 响应（L1 负载去掉 L1 头之后）：

```
[L2 头][L2 响应码 1B][...]
```

- 开始/结束会话：`...` 为 L3 响应码 2 字节（大端）
- 数据帧：`...` 为 `ctrl(1B) + func(1B) + L3 响应码(2B, 大端) + 数据`

L2 响应码：

| 值 | 含义 |
| --- | --- |
| 0 | 成功 |
| 2 | 设备要求重新开始任务 |
| 8 | 设备要求重发上一帧 |
| 9 | 设备内部错误 |
| 10 | 密码错误 |

L3 响应码：0 成功，其余为错误；10 同样表示密码错误。

## 4. Job 流程

每个 Job 都是一组固定的会话序列：

```
session 0 开始 -> session 0 结束          （任务开始）
group 1 开始  -> 若干条 L3 数据 -> 结束
group 2 开始  -> 若干条 L3 数据 -> 结束
session 1 开始 -> session 1 结束          （任务结束）
```

会话开始/结束帧都带登录块，登录块首字节必须是**当前 L2 会话 ID**。

### 4.1 连接确认

```
session 2: ctrl=1 func=0 payload=01
```

### 4.2 登录

```
session 3: ctrl=0 func=0   （读设备能力，原 SDK 的 j.b，基础 76 字节）
session 4: ctrl=2 func=0   （状态回报 o.a，用于登录后立即显示）
```

能力表用于按机型裁剪界面，详见第 11 节。基础表为 76 字节；电力/换气等条件块由机型决定是否追加，
40MAAC 只回 76 字节，因此没有这些附加块。

原 SDK 里这两个会话还有 `ctrl=0 func=3`（读设置）、`ctrl=2 func=6`（读时间），但它们由机型能力位
（`P0()`）决定，40 系列多联机不发。真机实测发 `func=3` 会返回 L3 码 `0x0059`，整个登录 Job 直接失败，
所以这里固定不发。

### 4.3 状态轮询

```
session 4: ctrl=2 func=0
```

### 4.4 控制

```
session 4: ctrl=1 func=1  控制 payload（17 字节）
           ctrl=2 func=0  回读状态
```

写命令的 L3 回执码非 0 表示设备拒绝这次设置（例如 40MAAC 上设置上下风向回 `0x3018`、百叶回 `0x1018`），
此时回读的状态仍是真实值。原 SDK 把非 0 一律当失败处理。

## 5. 登录块（7 字节）

| 字节 | 含义 |
| --- | --- |
| 0 | L2 会话 ID（0=任务开始，1=任务结束，3/4/...=数据会话） |
| 1 | 用户类型：0=访客，1=普通用户，2=管理员/服务 |
| 2 | 用户密码第 3、4 位（`pass[2]<<4 \| pass[3]`） |
| 3 | 用户密码第 1、2 位（`pass[0]<<4 \| pass[1]`） |
| 4 | license 类型 |
| 5 | license 密码第 3、4 位 |
| 6 | license 密码第 1、2 位 |

密码是 4 位十六进制字符，按 nibble 反序打包。例如 `32BC` → `BC 32`。

- 访客：user_type=0，密码 `AAAA`，license_type=0，license 密码 `0000`
- 普通用户：user_type=1，用户密码，license_type=0，license 密码 `0000`

## 6. 位域打包规则

原 SDK 先按字段声明顺序累加位宽，每满 8 bit 分成一组；然后**把组内字段顺序反转**，再按 MSB→LSB 写入。

净效果：

- 组内**先声明**的字段落在**低位**
- 多字节数值字段低字节在前、组内大端

例如登录块第一组 `session_type(6) + reserved(2)`，反转后 `reserved` 在高 2 位，`session_type` 在低 6 位，所以 `byte0 = sessionId & 0x3F`。

## 7. 温度编码（2 字节）

```
byte0 = ones << 4 | tenths
byte1 = sign << 7 | hundreds << 4 | tens
```

- 25.0 °C → `50 02`
- -5.5 °C → `55 80`
- `FF FF` 表示无效

| 0 | bit0=电源变更标志，bit1=模式变更标志 |
| 1 | bit0=制冷温度标志，bit1=制热，bit2=自动，bit3=节能上限，bit4=节能下限 |
| 2 | bit0=风速，bit1=上下风向，bit2=百叶，bit3=换气，bit4=保持，bit5=左右风向，bit6=人感，bit7=内部清洁 |

## 10. 时序与容错

- 单帧等待响应超时 6 秒，最多重试 3 次。
- 设备回 L2 响应码 8（要求重发）时，用同一个 `seq` 重发。
- 设备回 L2 响应码 2（要求重新开始任务）时，立刻断开重连：设备侧的旧会话只有断开才清得掉，
  在同一条链路上重跑 Job 只会一直回 2（原 SDK 也是断开重连后重跑，最多 10 次）。
- 非访客登录前先校验 4 位十六进制密码格式，格式错误直接提示，不进入重连循环。
- 链路断开或写入连续启动失败时，当前事务立即失败，交由连接监督循环重连。
- 重连采用指数退避：1s、2s、4s、8s、16s 封顶；设备要求重启任务时退避重置为 1s。
- 所有 L2/L3 事务由同一把互斥锁串行化，轮询与控制不会交叉。
- 断线/重连时会清空未发出的帧队列，避免旧命令写到新连接上。
